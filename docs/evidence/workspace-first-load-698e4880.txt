ROOT CAUSE (reproduced locally)
- app/(studio)/onboarding/page.tsx called bootstrapFirstWorkspace() during Server Component render. lib/auth/workspace-actions.ts called revalidatePath("/", "layout") after the successful RPC, inside the same try/catch. The RPC committed the workspace/membership/preferences rows, then Next.js 16.4.5 threw the render-phase invariant: "Route ...: `revalidatePath("/")` can't be called during render. Call it from a Server Action or Route Handler instead." The catch returned the owner-visible temporarily-unavailable message even though setup had succeeded. A manual refresh re-ran getWorkspaceContext(), found the committed rows and redirected to /account.
- Reproduction: a temporary Next dev page rendered revalidatePath("/", "layout") and returned HTTP 200 with exactly that thrown invariant; a temporary /api Route Handler returned NO_THROW for the same call. A deterministic regression test now mocks that invariant after a successful RPC and asserts the old catch result, while source/source-path tests assert the production render path no longer calls bootstrap.
- This was a render-phase mutation/cache-invalidation defect, not an SMTP/Auth, DB trigger, RPC security, RLS or client-polling failure. The SDK/source review also shows signInWithPassword()/verifyOtp() await session storage and subscribers before the post-auth redirect, and @supabase/ssr awaits cookie setAll; the proxy refreshes claims and private, no-store HTML.
